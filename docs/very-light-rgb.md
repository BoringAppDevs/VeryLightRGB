# Very Light RGB — оцінка та архітектура

Статус: початковий архітектурний план, реалізовано 2026-11-01 у native версії 1.0. Нижче збережені дослідження та початкові критерії; фактичний стан — у [README](../README.md), деталі реалізації — у [native/README](../native/README.md), результати перевірок — у [рев’ю](review-native-v1.md). Нова версія встановлена; повторний запуск через Планувальник, збереження налаштувань і подієве відновлення після контрольованого збою перевірені. Наступний реальний logon / reboot ще не виконувався.

## Рекомендована конструкція

Нативний C++ / Win32 фоновий процес і текстовий інтерфейс, що працює окремим процесом лише під час налаштування. Не потрібні WinForms, CLR/JIT або постійно відкрита консоль. Текстове меню саме по собі не гарантує малої пам’яті: якщо зберегти .NET чи інший великий runtime, значна частина витрат залишиться. Для порівняння, [Native AOT у .NET також спрямований на зменшення пам’яті](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), але його обмеження потребують переробки поточних WinForms і dynamic COM. Для пріоритету мінімального фону доцільний прямий Win32.

- `VeryLightRGB.exe --background`: маленьке приховане вікно для повідомлень tray, живлення та USB; читання конфігурації один раз; модулі пристроїв; один годинник анімацій.
- `VeryLightRGB.exe --menu`: окремий процес із TUI. Подвійний клік по tray запускає його або повертає фокус на вже відкрите меню. Обмін командами через локальний named pipe. Закриття меню завершує процес TUI, підсвітка продовжує працювати.
- Сталий колір: один запис, жодного циклу кадрів; сесія обладнання звільняється, де це дозволяє контролер. Анімація: підготовлені RGB-буфери, очікування таймера, відсутність busy loop, надсилання лише змінених кадрів. Жодного глобального підвищення частоти системного таймера.
- Збереження шести ефектів, загального та окремих стилів, кількості діодів, напрямку, зміщення, потужності й автозапуску. Профілі не повертаються.
- Назви виходів беруться з описів контролерів; «MSI · ARGB 1», а не назва моделі вентиляторів. Три паралельні вентилятори залишаються однією адресованою зоною.

Приклад меню:

```text
┌─ Very Light RGB ──────────────────────────┐
│  ● Світло ввімкнене                       │
│                                          │
│  Вихід       [ MSI · ARGB 1          ▾ ]  │
│  Стиль       [ Спільний               ]  │
│  Ефект       [ Темний блок по колу   ▾ ]  │
│  Колір       [ #C65CFF ]  Яскравість 15%  │
│  Діодів      [ 12 ]       Темних     [4]  │
│                                          │
│  [Пристрої]  [Reload devices]  [Система]  │
│  ↑↓ вибір   ←→ зміна   Enter   Esc        │
└──────────────────────────────────────────┘
```

Параметри залежать від ефекту та можливостей виходу; веселка не отримує зайвих параметрів. Додаткову пам’ять console host / Windows Terminal потрібно рахувати під час відкритого меню. Вона не має залишатися фоновою залежністю після закриття TUI.

## OpenRGB: що можливо

[OpenRGB SDK](https://openrgb.org/sdk.html) — мережеве керування контролерами запущеного сервера. Він не експортує самодостатній USB/I²C драйвер у JSON. Отримати список пристроїв і зон та зберегти вибір можна. Закрити OpenRGB і далі універсально керувати будь-яким із цих пристроїв лише за отриманими ID — не можна без окремої реалізації його протоколу у нашій програмі.

Два транспорти нового застосунку:

1. **Native:** перенести вже перевірені MSI HID і Gainward NVAPI. OpenRGB для цих пристроїв не потрібен. Нові нативні модулі додаються за конкретними протоколами, а не шляхом підстановки адрес із каталогу.
2. **OpenRGB:** необов’язковий сервер для решти сумісного обладнання. Враховувати його RAM та CPU у загальному бюджеті. Варіант для оцінки — [сторонній openrgb-headless](https://github.com/hello-nexus/openrgb-headless): автор прибрав Qt та GUI, залишив драйвери і SDK-сервер. Його споживання, сумісність із нашими пристроями та придатність для постачання ще не перевірено; розмір EXE не є заміром RAM.

Транспорт потрібно вибирати на рівні контролера, щоб підтримати MSI/Gainward нативно та, наприклад, мишку через SDK. Один контролер має тільки одного власника. У OpenRGB потрібно виключати контролери, якими керує native backend, включно з їхніми детекторами. Початковий універсальний скан та керування пристроями — різні операції.

## Каталог і повторне підключення

При initial setup / `Reload devices` зберігати модель, serial/location за наявності, VID/PID та інтерфейс, тип нативного модуля або SDK backend, зони, можливості, вручну відкалібровану довжину ARGB, вибір керованих виходів і стилі.

При звичайному запуску читати каталог і відкривати лише вибрані відомі пристрої. Швидкий пошук актуального USB-інтерфейсу потрібен навіть із кешем: після зміни порту або перепідключення handle / шлях може змінитися. Це не повний пробний скан апаратних шин.

За [протоколом SDK](https://gitlab.com/CalcProgrammer1/OpenRGB/-/blob/master/Documentation/OpenRGBSDK.md), формати 0–5 використовують індекси; формат 6 додає ID та повідомлення про зміну списку. Ці ID не слід вважати гарантовано постійними між запусками сервера. При новій сесії потрібне коротке зіставлення з актуальним каталогом сервера; це не повторне фізичне сканування нашим клієнтом. Повний скан сервер може виконувати під час власного запуску незалежно від нашого кешу.

Немає періодичного повного сканування. Події Windows про підключення / відключення USB можуть запускати відновлення відомого пристрою; для невідомого — пропозицію оновити каталог. SDK повідомлення про зміну пристроїв також обробляються подієво. Недійсний кеш не використовується для пробних записів невідомому пристрою.

## Razer та VIA

Razer потрібно перевіряти за точною моделлю, USB VID/PID та режимом підключення у [списку OpenRGB](https://openrgb.org/devices_1.1.html). Підтримка бренду не гарантує кожну модель або однакову роботу кабелю, донгла та Bluetooth.

Підтримка VIA сама по собі не гарантує OpenRGB. [VIA](https://caniusevia.com/docs/specification/) описує власні можливості освітлення клавіатури; [QMK-OpenRGB](https://gitlab.com/OpenRGBDevelopers/QMK-OpenRGB) є окремим модулем протоколу. Потрібні конкретна модель і перевірка її прошивки. Можливий нативний VIA backend для доступних налаштувань кольору / апаратних ефектів; це не автоматична гарантія покадрового керування кожним діодом або окремого lightbar. Прошивку в межах цього дослідження не змінено.

## Перевірка мінімального впливу

Початковий критерій: зробити малий нативний прототип tray + MSI/Gainward і виміряти реальну пам’ять до перенесення всього меню. Виконано: прототип приблизно 11,5 МіБ; повний агент із поточною анімацією приблизно 14,8 МіБ замість повідомлених користувачем приблизно 80 МБ попередньої версії. Це різні вимірювання, без паралельного A/B заміру. OpenRGB у ці 14,8 МіБ не входить і для поточного native backend не запускається.

Заміряти щонайменше 60 секунд після прогріву в чотирьох сценаріях: сталий колір із закритим меню, анімація із закритим меню, відкрите TUI, SDK режим. Рахувати суму процесів agent + TUI + console host + OpenRGB; окремо показувати working set, private commit, CPU одного ядра та CPU всього ПК. Не використовувати примусове витіснення working set як спосіб показати штучно низьку RAM.

Перенести перевірки пакетів та меж ефектів, додати тести кешу / повторного зіставлення / IPC, фізично перевірити обидва нинішні контролери, закриття TUI без зупинки світла, logon / resume та запуск через Планувальник зі справжньою конфігурацією. Для auto-start потрібне фактичне підтвердження обраного кольору / ефекту й набору виходів у журналі. Нову реалізацію перевірити перед заміною поточної.
