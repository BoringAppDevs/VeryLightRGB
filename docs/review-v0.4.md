# RGB Tray 0.4: рішення, рев’ю та перевірки

Дата: 2026-11-01. Це самоперевірка реалізації та автоматизовані тести; незалежне рев’ю іншим розробником не проводилося.

## Порівняння програм

| Програма | Перевірений функціонал | Рішення для RGB Tray |
|---|---|---|
| [OpenRGB](https://openrgb.org/) | Єдиний інтерфейс для різних брендів, апаратні контролери, [SDK для сторонніх програм](https://openrgb.org/sdk.html) | Відокремити опис зон від драйвера; додати необов’язковий локальний SDK backend для інших ПК |
| [SignalRGB Layouts](https://docs.signalrgb.com/guides/device-configuration/about-layouts/) | Спільний просторовий ефект, розташування / поворот / масштаб пристроїв, налаштування контролерів | Взяти спільний годинник і синхронний стиль; залишити прості напрямок і зміщення замість просторового редактора |
| [Artemis](https://github.com/Artemis-RGB/Artemis) | Редактор поверхні, налаштовувані ігрові ефекти, модулі для різних брендів | Розділити ефекти та транспорт. Власні колір / ефект кожної зони достатні для поточного обсягу |

Це порівняння документації та архітектури, а не вимірювання поточного споживання ресурсів конкурентів. Ігрові інтеграції, аудіовізуалізація, screen capture, 2D canvas, магазин ефектів і профілі не реалізовані. Профілі прибрані за прямим уточненням користувача.

## Меню після уточнень

Три вкладки: «Підсвітка», «Пристрої», «Система». Головна показує лише вибрані виходи. «Усе разом» змінює спільний стиль; прапорець прив’язки дозволяє власний стиль пристрою. Майстер-вимкнення має пріоритет над обома. Кількість LED доступна без розгортання додаткових параметрів, як загально, так і на окремому ARGB-виході. Веселка — фіксований ефект без прихованої залежності від попереднього кольору, швидкості або яскравості.

Вкладка «Пристрої» явно розрізняє доступний роз’єм і визначений контролер. Три хедери підтверджені [специфікацією MSI](https://www.msi.com/Motherboard/MAG-B850M-MORTAR-WIFI/Specification): 3 × JARGB_V2. Це не означає три підключені вентилятори. У користувача зайнятий один вихід. Для звичайних TL-K12 використаний HID-протокол не дає достовірної ознаки зайнятості; USB readback не є доказом підключення або свічення LED. Фактичний номер визначений користувачем візуально після основного рев’ю — див. результат тесту нижче. Нові MSI-виходи початково вимкнені для керування.

## Результати рев’ю

| Перевірка / проблема | Результат |
|---|---|
| Запис одного хедера міг би переписати сусідні зони | NativeSession змінює лише його 16 байт; чистий тест перевіряє весь решту config, апаратний тест підтверджує збереження невибраних зон |
| Один відсутній пристрій міг блокувати решту | Відкриття і статус кожної зони окремі; сценарій часткового збою перевірений fake backend |
| Незалежна анімація могла переписувати статичну сусідню зону | Сталі зони пишуться один раз, кадри надсилаються лише активним анімованим зонам; тест підраховує записи |
| Загальне off могло залишати незалежний стиль активним | RunPlan примусово вимикає всі стилі; перевірено тестом |
| Статичний режим утримував би потік / доступ до обладнання | Worker завершується після налаштування; сесія і mutex звільняються; перевірено fake та фізичним тестом |
| Зміна стилю спричиняла б спалах базового кольору | При перебудові плану restore вимкнений; при виході / sleep відновлення задається явно |
| Контролер MSI інколи повертає попередній config | До шести читань із паузою 15 мс без повторного запису. У перевіреній прошивці post-frame read може повернути ID 0x50; виняток дозволений тільки для цього читання |
| SDK transient indexes після перестановки пристроїв | Стійкі ID за метаданими контролера й зони; при повторній сесії ID зіставляються з актуальними індексами. Дублікати відхиляються |
| SDK повідомляє зміну переліку пристроїв | Сесія остаточно стає недійсною, подальші записи старими індексами відхиляються. Для продовження потрібен пошук |
| SDK неповні TCP-пакети, великі / некоректні дані | ReadExactly, таймаути, межі розміру / кількості / довжини, strict UTF-8, перевірка сигнатури та відповіді. Протокол звірений з [офіційною специфікацією](https://gitlab.com/CalcProgrammer1/OpenRGB/-/blob/master/Documentation/OpenRGBSDK.md) |
| Невідоме обладнання | Точні модельні guards у нативному транспорті; невідомі моделі не отримують пробних записів |
| Зайві налаштування веселки, прихована кількість LED | Виправлено; регресійні тести перевіряють реальні WinForms controls і сценарії зміни довжини / ефекту / прив’язки |
| Пробне підсвічування невибраного виходу залишало білий колір | Тимчасовий імпульс завершується чорним, потім застосовується збережений план керованих виходів |
| Зайві профілі | UI, типи й серіалізація видалені. Тест перевіряє відсутність вкладки та поля JSON |

## Виконані перевірки

- `dotnet run --project tests/RgbTray.Tests -c Release`: **7 557 assertions**, без RGB I/O. Модель налаштувань, міграція 0.3, незалежні стилі, генератори кадрів, границі циклів, згасання, напрямок / зміщення, фіксована веселка, звільнення runtime, регресії меню, SDK через локальний тестовий TCP-сервер.
- `dotnet run --project tests/RgbTray.Tests -c Release -- --hardware-effects`: **7 589 assertions**, разом із фізичними MSI / Gainward. Різні статичні кольори хедера та GPU, незмінність інших зон, живі кадри заповнення / темного блоку, виключний mutex, скасування до ініціалізації, повторний Stop, повернення сталого кольору. Стан конфігурації відновлений; settings.json тест не змінює.
- Release build: без попереджень або помилок. Збірка забороняє compiler warnings.
- Опублікований single-file EXE встановлений у `%LOCALAPPDATA%\Programs\RgbTray`; SHA-256 встановленого файлу збігається з артефактом. Автозапуск указує на нього з `--tray`. Шестисекундний smoke test установленого EXE завершився успішно: 157 змінених кадрів, усі налаштовані виходи без помилок (`local/v0.4-installed-effect.json`). Це підтверджує обмін із контролерами, а не фізичну зайнятість усіх виходів.
- Короткий замір прихованого tray під час «По черзі» з трьома раніше вибраними хедерами й GPU: working set 76,4 МБ, private memory 31,1 МБ, CPU 1,54% одного ядра за 3,04 с (`local/v0.4-resources.json`). Це одиничний короткий замір, не гарантія сталого споживання; зі сталою підсвіткою потік кадрів завершується.
- Accessibility tree запущеної програми підтвердило нові вкладки. Перевірка фінального меню кліками / знімком не завершена: Windows повернула `GetCursorPos: Access is denied`; desktop capture був порожній. Замість заяви про візуальне підтвердження виконано тести control states на STA-потоці. Остаточне візуальне приймання залишається за користувачем.

## Визначення зайнятого виходу

Після основної перевірки виконано `--map-headers`: ARGB 1 червоний, 2 зелений, 3 синій. Користувач підтвердив червоний колір вентиляторів. Отже, фізично використовується вихід **ARGB 1, індекс протоколу 0**. У settings.json залишені керованими лише цей вихід і GPU. За уточненням користувача власну назву вентиляторів прибрано: поле Name порожнє, інтерфейс використовує назву хедера з опису контролера — «MSI · ARGB 1». Інші стилі й кількості LED збережені. Повторний шестисекундний тест установленого EXE пройшов саме з двома вибраними виходами (`local/selected-header-effect.json`), після нього звичайна програма запущена зі збереженою анімацією. Це візуальне зіставлення за участі користувача, не автовизначення зайнятості.

## Практичні межі

Нативні драйвери перевірені лише на цьому поєднанні моделей і прошивки. Це не універсальний самостійний RGB-драйвер для будь-якого ПК. OpenRGB backend перевірений протокольними тестами, але не реальним сервером із стороннім обладнанням. Його custom mode працює на рівні контролера, тому може впливати на невибрані зони. Кількість SDK-діодів налаштовується в OpenRGB, тут не виконується resize / flash.

Немає фізичного читання LED, автоматичного визначення зайнятого TL-K12-хедера або поділу трьох паралельних вентиляторів на незалежні пристрої. USB / I²C збій може залишити останній кадр; програма показує помилку, але не доводить фізичний стан лампочок. Межі безпечного підключення й електричні навантаження визначає обладнання.
